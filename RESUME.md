# Loquela — Architecture & Implementation Reference

This document is the technical source of truth for Loquela. It is written primarily for developers who need to modify, extend, or reimplement the app. It describes **what each file is for, what it must contain, and how the pieces connect**.

Read the whole file before writing code.

---

## 1. Purpose

Loquela is a single-user, self-hosted Latin learning app. It is inspired of Duolingo's exercise loop, scoped to Latin, with three courses.
The app is small on purpose:

- No authentication.
- No database.
- No build step.
- No client-side framework.
- No external services.

All state lives in plain files. All content is plain JSON. All rendering is server-side EJS plus a small vanilla JS engine per exercise type.

**Everything in the app — code, comments, documentation, UI strings, JSON content, error messages — is in English.**

---

## 2. Non-goals

To prevent scope creep:

- No user accounts, no login, no multi-user.
- No cloud sync, no export/import.
- No spaced repetition algorithm (v1).
- No audio, no speech recognition.
- No mobile app, no PWA.
- No i18n. The app is English-only.
- No admin UI. Content is edited by hand in JSON.

If any of the above is ever needed, it is a **new project**, not a patch.

---

## 3. High-level architecture

Three layers, each completely decoupled from the others:

```
┌─────────────────────────────────────────────────────────────┐
│  courses/                     ← content (data, not code)    │
│    JSON files, editable by hand, validated on load          │
└─────────────────────────────────────────────────────────────┘
             ▲
             │ read at startup, cached in memory
             │
┌─────────────────────────────────────────────────────────────┐
│  src/app/                     ← application (Node.js)       │
│    Express server + EJS views + static client JS            │
└─────────────────────────────────────────────────────────────┘
             ▲
             │ one HTTP POST per completed lesson
             │
┌─────────────────────────────────────────────────────────────┐
│  progress.json                ← state (autogenerated)       │
│    Single file, atomic writes, deletable for hard reset     │
└─────────────────────────────────────────────────────────────┘
```

Each layer has a clear contract:

- **Content** is authored externally (often by an AI). It must conform to the schemas in §7. The app never writes to it.
- **Application** reads content, serves it, shuffles it, and records outcomes. It has no business logic beyond orchestration.
- **State** is written only by the app, only via `POST /api/lessons/:id/complete`.

The three layers can each be replaced independently. That is the whole design goal.

## 5. Technology decisions

| Decision | Choice | Rationale |
|---|---|---|
| Runtime | Node.js ≥ 18 | Native fetch, ESM support, LTS. |
| HTTP framework | Express | Minimal, ubiquitous, nothing to learn. |
| Templating | EJS | Requested. Server-side rendering, no client build. |
| Content format | JSON | Native to Node, human-writable, easy to validate. |
| Persistence | One `progress.json` file | Requested. No DB, atomic writes. |
| Client interactivity | Vanilla JS | No framework needed; feedback is synchronous. |
| CSS | Plain CSS with custom properties | No preprocessor, no Tailwind, no build. |
| Module system | ES modules (`import`/`export`) | Modern, consistent with Node 18+. |
| IDs | Kebab-case slugs | Readable in URLs and filenames. |

**Forbidden dependencies:** any ORM, any frontend framework, any CSS preprocessor, any test framework that requires a build step, any transpiler, TypeScript. The project must run with `npm start` after `npm install` with no additional tooling.

Permitted dependencies: `express`, `ejs`. Nothing else is required. If a solution seems to need a third dependency, prefer twenty lines of plain code first.

## 6. File-by-file specification

Every file below has a specific responsibility. Do not add responsibilities to a file that belongs to another.

### 6.1 Entry point

**`src/app/server.js`**
- Imports `express`, `path`, `config.js`, all routes, and the error middleware.
- Creates the Express app.
- Sets `view engine` to `ejs`, `views` to `src/app/views`.
- Sets up `express.static` pointing at `src/app/public`.
- Sets up `express.json()` (used by API routes).
- Mounts routers:
  - `routes/index.js` at `/`
  - `routes/courses.js` at `/courses`
  - `routes/lessons.js` at `/courses/:courseId/lessons`
  - `routes/api.js` at `/api`
- Mounts `middleware/errors.js` last (404 handler + error handler).
- On startup, calls `utils/courses.js#loadAll()` to load and validate every course and lesson. If any course fails to load, log the error and exit with a non-zero code. It is better to fail loudly than to serve broken content.
- Listens on `config.port`.

**`src/app/config.js`**
- Exports a single frozen object.
- Must contain:
  - `port` (default `3000`, overridable via `PORT` env var).
  - `rootDir` — absolute path to project root (two levels above `src/app`).
  - `coursesDir` — `path.join(rootDir, 'courses')`.
  - `progressPath` — `path.join(rootDir, 'progress.json')`.
- Every other file that needs a path must import it from here. No path is ever built inline outside this file.

### 6.2 Routes

Routes are thin. Each file imports the utils it needs, calls them, and either renders an EJS view or sends JSON. **No business logic lives in routes.**

**`src/app/routes/index.js`**
- `GET /` — renders `pages/index.ejs`.
- Passes to the view: `courses` (array of course summaries from `utils/courses.js#listCourses()`), and `progress` (object from `utils/progress.js#read()`).
- `courseSummary` shape: `{ id, title, subtitle, description, level, color, icon, lessonCount, completedCount }`.

**`src/app/routes/courses.js`**
- `GET /courses/:courseId` — renders `pages/course.ejs`.
- Loads the full course from `utils/courses.js#getCourse(id)`.
- If not found, calls `next()` with a 404 error.
- Passes to the view: `course` (full object with lessons list), `progress` (course-specific subset), and `lessonStates` (array of `{ id, title, state: 'locked'|'available'|'completed' }`).

**`src/app/routes/lessons.js`**
- `GET /courses/:courseId/lessons/:lessonId` — renders `pages/lesson.ejs`.
- Loads the lesson from `utils/courses.js#getLesson(courseId, lessonId)`.
- If not found or locked, calls `next()` with a 404.
- **Applies shuffling:** `const shuffled = shuffleLesson(lesson)`.
- Renders `pages/lesson.ejs` with the shuffled lesson embedded as JSON (see §9).

**`src/app/routes/api.js`**
- `POST /api/lessons/:courseId/:lessonId/complete`
  - Body: `{ xp, accuracy }` (accuracy is a number 0–1).
  - Calls `utils/progress.js#completeLesson(courseId, lessonId, xp, accuracy)`.
  - Returns `{ ok: true, progress: <updated progress object> }`.
- `POST /api/streak`
  - Touches the streak counter for today.
  - Returns `{ ok: true, streak: <streak object> }`.
- Both endpoints validate the course and lesson exist before writing.
- Never trust the client for XP amounts: recompute XP from the lesson's `xp` field server-side. The client's `xp` value is ignored.

### 6.3 Utilities

**`src/app/utils/files.js`**
- `readJson(path)` — synchronous read + `JSON.parse` with a clear error message containing the file path.
- `writeJsonAtomic(path, data)` — writes to `path + '.tmp'`, then `fs.renameSync`. Used exclusively by `progress.js`. 
- `exists(path)` — synchronous boolean.
- No other logic. This file is a thin wrapper over `fs`.

**`src/app/utils/validate.js`**
- Exports two functions:
  - `validateCourse(course)` — throws `Error` with a descriptive message if the object does not match the schema in §7.1.
  - `validateLesson(lesson)` — same for §7.2, including per-exercise-type field validation for every exercise.
- Validation is **strict and eager**: every required field must be present, every type must be one of the six supported, every index must be in range, etc.
- No coercion, no defaults, no partial validation. If a lesson fails, the app refuses to start.

**`src/app/utils/courses.js`**
- In-memory cache of all courses and lessons.
- `loadAll()` — called once at startup:
  - Reads every directory under `config.coursesDir`.
  - For each: reads `course.json`, runs `validateCourse`, then for each ID in `course.lessons`, reads `lessons/<id>.json` and runs `validateLesson`.
  - Populates an internal `Map<courseId, Course>`, where each `Course` contains its `course.json` data plus a `lessonMap: Map<lessonId, Lesson>`.
  - On any failure, throws so `server.js` exits.
  - After loading, runs `detectAIPatterns()` on every lesson and logs warnings (see §8.5). Does not throw on warnings.
- `listCourses()` — returns array of course summaries (no lessons).
- `getCourse(id)` — returns full course with `lessons` as an array of `{ id, title, subtitle, xp }` (metadata only, not exercises).
- `getLesson(courseId, lessonId)` — returns the full lesson object, **unshuffled**. Shuffling is applied by the route, not here.
- `existsCourse(id)` / `existsLesson(courseId, lessonId)` — booleans.

**`src/app/utils/progress.js`**
- Reads `config.progressPath` at startup. If the file doesn't exist, creates it with the default shape (§10) and writes it.
- `read()` — returns the current in-memory progress object.
- `completeLesson(courseId, lessonId, xp, accuracy)`:
  - Validates the lesson exists and is not already completed.
  - Adds `lessonId` to `courses[courseId].completedLessons`.
  - Adds `xp` to `courses[courseId].xp`.
  - Recomputes `currentLesson` as the first lesson in `course.lessons`
    not in `completedLessons`.
  - Updates `lastPlayed` timestamps.
  - Writes atomically.
  - Returns the updated object.
- `touchStreak()` — updates `streak.current`, `streak.longest`, `streak.lastDay` based on today's date. Writes atomically.
- All writes go through `writeJsonAtomic`.

**`src/app/utils/shuffle.js`**
- Exports `shuffleLesson(lesson)` and `detectAIPatterns(lesson)`.
- The full contract is in §8.

### 6.4 Middleware

**`src/app/middleware/errors.js`**
- Exports a single `errorHandler(err, req, res, next)`.
- If `err.status === 404`, renders a plain 404 page (or returns JSON if the request path starts with `/api`).
- Otherwise logs the error and returns a 500.
- In all cases, does not leak stack traces to the browser.

### 6.5 Views (EJS)

All views extend `layout.ejs` unless documented otherwise.

**`src/app/views/layout.ejs`**
- The HTML shell: `<html>`, `<head>`, `<body>`.
- Injects:
  - Google Fonts (Cinzel + Inter) as `<link>`.
  - `public/css/tokens.css`, `base.css`, `components.css`.
  - A `<%- body %>` slot for page content.
  - `<%- scripts %>` slot for page-specific JS.
- Provides `<title><%= title %> · Loquela</title>`.

**`src/app/views/pages/index.ejs`**
- Grid of three `courseCard.ejs` partials.
- Each card shows: title, subtitle, description, lesson count, completion count, and a link to `/courses/:id`.

**`src/app/views/pages/course.ejs`**
- Renders the lesson map: a vertical column of `lessonNode.ejs` partials.
- Header shows course title, subtitle, XP, and current streak.
- Each node links to its lesson if `state !== 'locked'`, otherwise shows a lock icon and no link.

**`src/app/views/pages/lesson.ejs`**
- The lesson shell:
  - Progress bar (filled by JS as the user advances).
  - Close button returning to `/courses/:courseId`.
  - `<div id="exercise-root"></div>` where exercises mount.
  - Embeds the shuffled lesson as JSON:
    ```html
    <script id="lesson-data" type="application/json">
      <%- JSON.stringify(lesson) %>
    </script>
    ```
  - Embeds the course ID and lesson ID as data attributes.
  - Includes `public/js/lessonEngine.js` and `public/js/ui.js`.
  - Includes each exercise handler in `public/js/exercises/*.js`.

**`src/app/views/partials/*.ejs`**
- Small reusable components: header, footer, course card, lesson node.
- Must not contain business logic.

**`src/app/views/exercises/*.ejs`**
- Server-side templates for each exercise type. They receive a single `exercise` object.
- The client engine will re-render them on the fly? **No.** The EJS partials
  are used for the *initial* page render only. All subsequent exercises are
  rendered client-side by the corresponding handler in
  `public/js/exercises/`. This is a deliberate choice to keep the client
  responsive without a client-side templating engine.
- Each partial must produce the same DOM structure that the client handler
  produces, so the visual language stays consistent.

### 6.6 Client JS

**`src/app/public/js/lessonEngine.js`**
- Reads `#lesson-data`, parses it.
- Maintains state: `{ exerciseIndex, correctCount, startTime }`.
- Renders the current exercise via the matching handler from
  `window.LoquelaHandlers[exercise.type]`.
- Handles "Check", "Continue", and "Skip" buttons.
- On lesson complete: `POST /api/lessons/:courseId/:lessonId/complete` with
  `{ accuracy }`. Server recomputes XP. Client then `POST /api/streak`,
  then redirects to `/courses/:courseId`.
- Registers every exercise handler in a global object so handlers stay
  independent.

**`src/app/public/js/exercises/*.js`**
- One file per exercise type.
- Each exports `{ render(exercise, container), validate() }`.
- `render` builds the DOM.
- `validate` returns `{ correct: boolean, explanation?: string }`.
- The engine calls `validate`, shows feedback, then advances.
- **No exercise handler ever sees the raw `correctIndex` as an "original"
  value** — it always sees the shuffled version, because the server shuffled
  before embedding. This keeps handlers dumb and simple.

**`src/app/public/js/progress.js`**
- Wraps the two API calls. Not strictly necessary but keeps `lessonEngine`
  readable.

**`src/app/public/js/ui.js`**
- Toasts, feedback panel slide-in, confetti on correct (respecting
  `prefers-reduced-motion`), sound-less by default.

### 6.7 CSS

- `tokens.css` — only CSS custom properties. No selectors. Defines the
  palette and typography tokens from §11.
- `base.css` — resets, body defaults, typography scale.
- `components.css` — buttons, cards, progress bars, badges, feedback panel.
- `lesson.css` — exercise-specific layouts, progress bar, feedback colors.

## 7. Data schemas

All JSON files are UTF-8, indented with 2 spaces, and must not contain
comments. Field names are lowercase kebab-case.

### 7.1 `course.json`

```json
{
  "id": "cotidiano",
  "title": "Sermo Cotidianus",
  "subtitle": "Everyday Latin",
  "description": "The Latin you actually use: weather, routine, small talk.",
  "level": "A2-B1",
  "color": "#2D5D3E",
  "icon": "laurel",
  "order": 2,
  "lessons": [
    "01-greetings",
    "02-weather",
    "03-morning-routine"
  ]
}
```

Required fields: `id`, `title`, `subtitle`, `description`, `level`,
`color`, `icon`, `order`, `lessons`.

- `id` must match the folder name.
- `lessons` must list every file in `lessons/` in the desired order. The
  array is the source of truth for ordering; filenames are just labels.

### 7.2 Lesson file

```json
{
  "id": "02-weather",
  "title": "De Caelo",
  "subtitle": "The weather",
  "description": "Talk about sun, rain, cold, and wind.",
  "xp": 15,
  "order": 2,
  "shuffle": true,
  "completionMessage": "Caelum serenum est!",
  "exercises": [ /* ... */ ]
}
```

Required fields: `id`, `title`, `subtitle`, `description`, `xp`, `order`,
`exercises`. Optional: `shuffle` (default `true`), `completionMessage`
(default `"Bene factum!"`).

- `id` must match the filename without `.json`.
- `exercises` must be a non-empty array.
- `xp` is an integer between 5 and 100.

### 7.3 Exercise types

Six types are supported. Every exercise object has a `type` field.

**`multiple-choice`**
```json
{
  "type": "multiple-choice",
  "prompt": "How do you say 'it is cold' in Latin?",
  "options": ["Frigus est", "Calor est", "Pluit", "Ningit"],
  "correctIndex": 0,
  "explanation": "Frigus est = 'it is cold'. Literally 'there is cold'."
}
```
Required: `type`, `prompt`, `options` (2–6), `correctIndex` (integer in
range). Optional: `explanation`.

**`translate`**
```json
{
  "type": "translate",
  "direction": "en-la",
  "source": "Today the weather is nice.",
  "correct": [
    "Hodie caelum serenum est.",
    "Hodie tempestas bona est."
  ],
  "hint": "Use 'hodie' for 'today'.",
  "explanation": "'Caelum serenum' is the most natural phrasing."
}
```
Required: `type`, `direction` (`en-la` or `la-en`), `source`, `correct`
(array of accepted answers). Optional: `hint`, `explanation`.
Validation compares the user's answer to each entry in `correct` after
normalization (lowercase, strip accents, collapse whitespace, strip
trailing punctuation).

**`matching`**
```json
{
  "type": "matching",
  "prompt": "Match each expression with its meaning.",
  "pairs": [
    { "left": "Pluit", "right": "It is raining" },
    { "left": "Ningit", "right": "It is snowing" }
  ]
}
```
Required: `type`, `prompt`, `pairs` (2–6 items, each with `left` and
`right`). Optional: `explanation`. Pairs are unordered; the shuffle layer
guarantees left and right columns are independently randomized.

**`order`**
```json
{
  "type": "order",
  "prompt": "Arrange the words to mean 'Today it is raining a lot'.",
  "tokens": ["Hodie", "multum", "pluit"],
  "correct": [
    "Hodie multum pluit.",
    "Hodie pluit multum."
  ]
}
```
Required: `type`, `prompt`, `tokens` (2–10 strings), `correct` (array of
complete sentences). Optional: `explanation`. The client builds the user's
sentence from the tokens in the order they were placed, then compares to
`correct` after normalization.

**`fill-blank`**
```json
{
  "type": "fill-blank",
  "prompt": "Complete the sentence.",
  "before": "Cras",
  "after": "sol lucebit.",
  "correct": ["sol"],
  "explanation": "The verb 'lucebit' is 'will shine'."
}
```
Required: `type`, `prompt`, `before`, `after`, `correct` (array of accepted
strings). Optional: `explanation`.

**`true-false`**
```json
{
  "type": "true-false",
  "prompt": "The word 'pluit' means 'the sun is shining'.",
  "correct": false,
  "explanation": "Pluit means 'it is raining'. 'Sol lucet' means 'the sun is shining'."
}
```
Required: `type`, `prompt`, `correct` (boolean). Optional: `explanation`.

## 8. The shuffle system

### 8.1 Why

Lesson content is generated by AI, and AI reliably produces structural
biases: `correctIndex: 0` in nearly every multiple-choice, `pairs` aligned
positionally, `tokens` already in sentence order, `correct: true` in most
true/false. The shuffle system neutralizes these biases at serve time so
the app is fair regardless of content quality.

**Do not rely on the AI to randomize.** The system must randomize.

### 8.2 Where

Shuffling happens **on the server, once per request**, in
`routes/lessons.js`, immediately after loading the lesson and before
rendering. It is **not** persisted to disk.

Consequences:
- The lesson JSON on disk is never modified.
- Each page reload produces a different permutation.
- No client-side shuffle code is needed.
- The client handlers always work on already-shuffled data — they never
  have to think about "original" vs "shuffled" indices.

### 8.3 API

```js
// src/app/utils/shuffle.js
export function shuffleLesson(lesson) {
  if (lesson.shuffle === false) return lesson;
  return {
    ...lesson,
    exercises: fisherYates(lesson.exercises).map(shuffleExercise),
  };
}

export function detectAIPatterns(lesson) { /* see 8.5 */ }
```

`shuffleExercise(ex)` dispatches on `ex.type`:

- **`multiple-choice`** — pair each option with `wasCorrect`, run
  Fisher-Yates, then rebuild `options` and recompute `correctIndex` as the
  new index of the correct option.
- **`matching`** — build `leftItems` and `rightItems` from the pairs and
  Fisher-Yates each independently. Keep `pairs` unchanged; the client uses
  it for validation only.
- **`order`** — Fisher-Yates `tokens`. Keep `correct` unchanged.
- **`translate`, `fill-blank`, `true-false`** — return unchanged.

### 8.4 Fisher-Yates (mandatory implementation)

Use Fisher-Yates (Knuth). **Do not use `Array.prototype.sort` with
`Math.random`** — it is biased and non-uniform.

```js
function fisherYates(arr) {
  const a = [...arr];
  for (let i = a.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [a[i], a[j]] = [a[j], a[i]];
  }
  return a;
}
```

### 8.5 QA pattern detection

`detectAIPatterns(lesson)` returns an array of warning strings. It is
called from `utils/courses.js#loadAll()` after each lesson is validated,
and each warning is logged with `console.warn`.

Detects:
- ≥3 `multiple-choice` exercises where every `correctIndex === 0`.
- ≥3 `true-false` exercises where every `correct === true`.
- Any `order` exercise whose `tokens.join(' ')` already equals one of its
  `correct` entries (after normalization).
- Any `matching` exercise whose `pairs` are already in matching order by
  content (i.e., a pair's `right` is the next entry's `left` — rare but
  possible).

**Warnings never fail loading.** They are signals for the content author
(typically the AI prompt writer) to improve the next generation pass.

## 9. Client–server contract

### 9.1 Lesson page render

`GET /courses/:courseId/lessons/:lessonId` returns full HTML. The lesson
object is embedded as:

```html
<script id="lesson-data" type="application/json">
  { ...the shuffled lesson object... }
</script>
```

The client only ever reads from `#lesson-data`. It never calls an API to
fetch a lesson.

### 9.2 Completion

After the last exercise, the client sends:

```http
POST /api/lessons/:courseId/:lessonId/complete
Content-Type: application/json

{ "accuracy": 0.83 }
```

The server:
1. Verifies course and lesson exist.
2. Verifies the lesson is not already completed (idempotent — returns the
   current progress object without double-counting XP).
3. Reads `xp` from the lesson (server-side), ignoring any client-supplied
   value.
4. Calls `progress.completeLesson(...)`.
5. Returns the updated progress object.

Response:
```json
{ "ok": true, "progress": { /* full progress object */ } }
```

### 9.3 Streak

```http
POST /api/streak
```

Called once per session, after the first completed lesson of the day.
Increments `streak.current` if `lastDay` is yesterday, resets to 1 if
older, leaves unchanged if today.

Response:
```json
{ "ok": true, "streak": { "current": 3, "longest": 7, "lastDay": "2026-10-26" } }
```

## 10. `progress.json` shape

```json
{
  "version": 1,
  "lastOpened": "2026-10-26T18:12:00.000Z",
  "streak": {
    "current": 3,
    "longest": 7,
    "lastDay": "2026-10-26"
  },
  "courses": {
    "cotidiano": {
      "xp": 45,
      "currentLesson": "03-morning-routine",
      "completedLessons": ["01-greetings", "02-weather"],
      "lastPlayed": "2026-10-26T18:10:00.000Z"
    }
  }
}
```

Rules:
- `version` must be `1`. Future migrations bump it.
- Missing courses are treated as `{ xp: 0, completedLessons: [],
  currentLesson: <first lesson>, lastPlayed: null }`.
- Deleting the file is a hard reset. The app regenerates it on next start.
- Writes are always atomic via `writeJsonAtomic`.
- The file is never written by anything other than `utils/progress.js`.

## 12. Adding a new exercise type

The system is designed to be extended, but only six types are in scope for
v1. If a seventh is ever added, the checklist is:

1. Add the type to `utils/validate.js` with its required fields.
2. Add a `shuffleExercise` branch in `utils/shuffle.js` (default: identity).
3. Create `views/exercises/<type>.ejs` (initial render).
4. Create `public/js/exercises/<type>.js` (render + validate).
5. Register the handler in `lessonEngine.js`.
6. Add CSS to `public/css/lesson.css`.
7. Document it in `docs/LESSON_SCHEMA.md`.

Any implementation that requires changes to `lessonEngine.js` beyond
registering a handler is wrong.

## 13. Adding a new course

1. Create `courses/<id>/` with `course.json` and `lessons/`.
2. Every lesson listed in `course.json.lessons` must exist as
   `lessons/<id>.json`.
3. Restart the app. The course appears automatically on the home page.
4. No code changes.

If the course fails validation, the app exits with an error pointing to the
offending file. Fix the file and restart.

## 14. Testing strategy

There is no test suite in v1. This is intentional: the app is small, the
user is the only tester, and a proper test suite would require a build
step that breaks the "plain Node" constraint.

Manual smoke test after any change:

1. `npm start` — the app boots without errors.
2. Home page lists all three courses.
3. Opening `cotidiano` shows the lesson map with the first lesson
   available.
4. Opening a lesson loads it, exercises render, feedback works, progress
   bar advances.
5. Completing a lesson returns to the map with XP updated and the next
   lesson unlocked.
6. `progress.json` is written atomically (check for `.tmp` leftovers — there
   should be none).
7. Reloading the same lesson shows a different exercise order (shuffle
   works).
8. Deleting `progress.json` and restarting resets everything.

If any of these fail, the change is not done.

## 15. AI content generation (out of scope for the code)

The `docs/AI_LESSON_PROMPTING.md` file contains the prompts used to
generate lesson JSON with an external AI. This is a content-authoring
concern, not a code concern. The app must always assume lesson JSON was
generated imperfectly and rely on the shuffle and validation layers to
guarantee a good experience.

The code must **never** assume that lesson JSON is well-formed beyond what
`validate.js` enforces. If a lesson passes validation, it must render
correctly after shuffling.

## 16. Summary of invariants

Any future change must preserve these:

1. `courses/` and `docs/` live at the project root, not under `src/`.
2. `src/app/` contains only `routes/`, `utils/`, `middleware/`, `views/`,
   `public/`, `server.js`, `config.js`. No `controllers/`, no `services/`.
3. Only `express` and `ejs` are runtime dependencies.
4. All paths are defined in `config.js`.
5. Shuffling happens in `routes/lessons.js` via `utils/shuffle.js`, never
   in the client, never persisted.
6. XP is recomputed server-side; the client never determines XP.
7. `progress.json` is written only by `utils/progress.js`, always
   atomically, and is always deletable for a hard reset.
8. All content is in English, except for the Latin being taught.
9. If a lesson file is malformed, the app refuses to start with a clear
   error message.
10. Adding a course requires no code changes. Adding an exercise type
    requires no changes to `lessonEngine.js` beyond handler registration.
